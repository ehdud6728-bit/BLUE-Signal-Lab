# Same-origin gateway review
No automatic deployment. The API's named service entrypoint validates the frontend application token, not a caller-supplied access flag. Direct API behavior and current static deployment remain unchanged until explicit gateway deployment.
Before any production deployment, compare both existing Cloudflare Access policies (users, groups, posture, session, deny/allow rules); frontend must not permit access beyond the API. Verify the exact frontend Application AUD and team domain. Set BLUE_WEB_ACCESS_TEAM and BLUE_WEB_ACCESS_AUD on the existing API Worker using the Cloudflare dashboard. No credentials or tokens go into browser storage.
Verify CI, then deploy the API entrypoint first using the existing guarded API deploy. The web gateway needs a separate explicit deployment, with VITE_API_BASE set to the existing frontend origin, using web/wrangler.gateway.jsonc. Do not use the existing static-only deploy to install a gateway or bypass its safety guard.
After gateway deployment, test the same existing web URL with authorized and unauthorized accounts, Safari/Chrome/PWA with default privacy settings, all read and write routes, and rollback. The named service entrypoint cannot be called as a public HTTP route. Preserve current web and API version IDs before any deployment. No D1/Turso/KIS writes or schema changes from this verification workflow.
